# AI ガードレール方針

この文書は、PR レビューで得られた知見を、**次に同じ間違いが起きないための仕組み**へ
変換する流れを扱う。個別のルールそのものは [`.agents/rules/rules.md`](../.agents/rules/rules.md) が正典であり、
ここではなぜその形にしたのかという設計判断を残す。

## 結論

レビュー指摘は、**収穫 → 昇格 → 強制**の 3 段で扱う。

```text
PR レビュー（CodeRabbit / 人間）
        │
        │  main への push で自動実行   収穫: 指摘を分類し、再発クラスタを候補として提示
        ▼                              （.github/workflows/harvest-rules.yml）
   ルール候補（2 件以上 かつ 修正実績あり）
        │
        │  採用済み・却下済みを差し引く
        ▼
   新しい候補があるときだけ Issue を立てる／更新する
        │
        │  人間が採否を決める          昇格: 出典 PR を添えて正典へ記載
        ▼                              採らないなら declined.md へ理由を記録
   .agents/rules/rules.md
        │
        │  判定可能性で振り分ける      強制: 機械が判定できるものは CI へ
        ▼
   test/project-rules.test.mjs  →  npm test / CI / lefthook pre-push
```

要点は次の 3 つである。

1. **1 件の指摘をルールにしない。** 再発したものだけ昇格させる。
2. **判定できるものを markdown に書かない。** markdown は助言、CI は強制。
3. **出典を必ず残す。** 根拠のないルールは、後から誰も消せなくなる。
4. **知らせるのは自動、決めるのは人間。** 候補の提示までを機械がやり、
   ルールを書く判断は人間が持つ。

## 背景

このリポジトリの PR には CodeRabbit のレビューが付いており、
指摘 → 修正 → 承認のログが残っている。これはルールの原料として理想的だが、
放っておくと同じ知見が PR の中に埋もれたままになる。

実際に、導入時点の実測でそれが起きていた。
PR#63 で `apps/vscode-extension/src/learning/sync.ts` に
「同期リクエストにタイムアウトを設定してください」という指摘を受けて対策したが、
**同じ対策が他の 4 箇所へ横展開されていなかった**。
一度レビューで学んだことが、別のファイルで再発していたということである。

レビューで学んだことが人間の記憶にしか残らないなら、
ファイルが変わり、担当が変わり、AI が書き始めた瞬間に失われる。

## 設計判断

### なぜ「2 件以上」を昇格条件にしたか

1 コメント = 1 ルールにすると、ルール集がすぐに数百行になる。
そうなった時点で誰も読まなくなり、AI に渡してもコンテキストを浪費するだけで守られない。
「がちごちにする」ことと「ルールを増やすこと」は同じではない。

再発は「このプロジェクトの構造上、繰り返し踏むポイント」であることの証拠になる。
1 回きりの指摘は、その場で直せば十分である。

### なぜ「修正実績あり」を条件に加えたか

nitpick として却下された指摘や、議論の末に採用されなかった提案を混ぜると、
ガードレールがノイズになる。ノイズが混ざったルール集は、最終的に全体が無視される。

判定には、著者の返信と、CodeRabbit 自身の「確認しました」という追随を使う。
後者は bot が修正の着地を確認したシグナルなので、より強い。

### なぜ強制手段を振り分けるのか

すべてを markdown に書くのが最大の失敗パターンである。
人も AI も、読んだうえで守り忘れる。

| 判定可能性         | 置き場所                                                 |
| ------------------ | -------------------------------------------------------- |
| 決定的に検査できる | `test/project-rules.test.mjs` / eslint                   |
| 人の判断が要る     | `.agents/rules/rules.md`（`AGENTS.md` から読み込まれる） |

上に落とせるものを下に落とさない。これが実効性の分かれ目になる。

### ルールをエージェントにどう届けるか

規約の置き場所は、エージェントが**自動で読む場所**に合わせる。

| ツール      | 自動で読むファイル   |
| ----------- | -------------------- |
| Claude Code | ルートの `CLAUDE.md` |
| Codex       | ルートの `AGENTS.md` |

このリポジトリは `CLAUDE.md` を `AGENTS.md` へのシンボリックリンクにしてあるので、
**両方が同じ 1 枚を読む**。Cursor の `.cursor/rules` に相当するものを別に用意する必要はない。

ただし「入口が読まれる」ことと「正典が読まれる」ことは別である。
`AGENTS.md` にリンクを置いて「必ず読むこと」と書いても、
それを開くかはエージェントの判断に委ねられる。指示であって機構ではない。

そこで `AGENTS.md` に次の 1 行を置いている。

```markdown
@.agents/rules/rules.md
```

Claude Code はこれを展開し、正典の全文を毎セッション無条件にコンテキストへ載せる。

**Codex はこれを展開しない。** 実測で確認した
（`rules.md` にしか無い記述を問うと「不明」と答える）。
そのため Codex 向けには `AGENTS.md` 内のルール一覧表が唯一の手がかりになる。
表には ID と要旨だけを置き、詳細は正典を開かせる。

正典を `AGENTS.md` へ丸ごと転記しないのは、`rules.md` を単一ソースに保つため。
代わりに、**表と正典の ID が一致していること**と
**`@` の行が消えていないこと**をメタテストで検査している。

### なぜ収穫を自動化し、ルールの執筆を自動化しないのか

`npm run harvest:rules` を手で叩く運用だと、**叩こうと思い出す仕組みがどこにもない**。
「増やし方」を文書に書いても、それは増やそうと決めた人が読む場所であって、
増やすべき時期を教えてはくれない。結果としてルールは増えない。

そこで、**知らせることだけを自動化した**。
`main` への push はマージされた PR がレビューごと入ってくる瞬間であり、
新しい原料が実際に増えるタイミングと一致する。

一方で、ルールの追記とテストの生成は自動化しない。
エージェントがルールを書き足せるようにすると、ルール集はすぐに
「誰も読まない長さ」へ膨らむ。この仕組みの価値は、
**ルールが少なく、1 件ずつが信用できる**ことにある。
Issue には貼り付け用の下書きを載せてあるので、書き写す手間は省けるが、
採るかどうかの判断は人間に残る。

### なぜ却下の記録が必要か

自動で知らせる以上、**同じ候補を何度も出さないこと**が生命線になる。
収穫は毎回すべてのレビューを読み直すので、何もしなければ同じ 6 クラスタを永久に提示し続ける。
同じ通知が繰り返されれば数週間で無視されるようになり、
自動化した結果として手動より悪くなる。

差し引きには 2 つの記録を使う。

- **採用済み** — `rules.md` の出典 PR 番号で判定する。新しい記録は要らない。
  修正実績のある指摘がすべて既に引かれていれば採用済みと見なす。
- **却下済み** — `.agents/rules/declined.md` に明示的に記録する。
  これが無いと、却下した候補と本当に新しい候補を区別できない。

**採らないことも決定である。** 出典を必ず残すという原則は、却下側にも同じく効く。

### なぜ生成器（`gen:rules`）を作らなかったか

このリポジトリには `gen:concepts` / `check:concepts` という
「単一ソースから生成し、CI で最新かを検証する」既存の型がある。
ルールも同じ形にする案を検討したが、**採用しなかった**。

理由は入力の規模である。ルールが 5 件の段階で生成パイプラインを組むと、
入力 5 行の生成器を保守することになり、機構のほうが中身より重くなる。
価値があるのは生成ではなく CI への配線のほうである。

ルールが 10 件を超えて手書きの重複が問題になった時点で再検討する。

### なぜ既存のメタテストの形に乗せたか

`test/package-scripts.test.mjs` が、リポジトリの構成そのものを
`node --test` で検査するという型を既に持っている。
これは `npm test` → CI → lefthook pre-push まで配線済みである。

新しい機構を発明せず、この型に乗せた。同じ形なので、読む側の学習コストがない。

## 運用手順

`main` に push されるたびに収穫が自動で走り、**新しい候補があるときだけ** Issue が立つ。
候補が無ければ何も起きない。手元で確認したいときは次を叩く。

```bash
npm run harvest:rules                # 全候補（採用済み・却下済みの印付き）
npm run harvest:rules -- --new-only  # まだ検討していないものだけ
```

候補が出たら、**必ずどちらかに倒す**。放置すると次の push でまた出てくる。

- **採用する** → `.agents/rules/rules.md` に出典 PR 付きで追記する。
  決定的に検査できるなら `test/project-rules.test.mjs` にテストを足す。
- **採用しない** → `.agents/rules/declined.md` に理由付きで記録する。

Issue には両方の下書きが載っているので、貼って埋めればよい。

## 実装

| 要素       | 実体                                                                            |
| ---------- | ------------------------------------------------------------------------------- |
| 収穫       | `scripts/harvest-review-rules.mjs`（`npm run harvest:rules`）                   |
| 自動起動   | `.github/workflows/harvest-rules.yml`（`main` への push / 手動）                |
| 通知の整形 | `scripts/format-rule-candidates.mjs`（Issue 本文と下書きを生成）                |
| 却下の記録 | `.agents/rules/declined.md`                                                     |
| 正典       | `.agents/rules/rules.md`（出典は PR 番号と対象パスの組で書く）、運用は この文書 |
| 強制       | `test/project-rules.test.mjs`（`npm run test:project-rules`）                   |
| 入口       | `AGENTS.md`（= `CLAUDE.md`）からルール一覧へ誘導                                |

### 配線が消えないようにする

ルール検査が npm script / CI / lefthook のどこからも呼ばれなくなると、
ファイルは残ったまま何も守らなくなる。これは緑のまま壊れるので気付けない。

そこで `test/package-scripts.test.mjs` に、**配線そのものを検査するテスト**を追加した。
`test:project-rules` が `npm test` から呼ばれ、CI のステップにあり、
lefthook の pre-push にあることを検査する。後から静かに外すことはできない。

## 導入時の実測

ガードレールを書いた時点で、現行コードに対して 7 件の違反を検出した。
これは「ルールを書いたが今日は何も見つからなかった」ではなく、
**仕組みが実際に機能することの証拠**である。

内訳は次のとおり。

- **3 件は誤検出だった。** SSE ストリーミングと逆プロキシで、
  一律のタイムアウトを入れると正常な応答が途中で切れるバグになる。
  → コードではなく**ルール側を分割して**対象外にした（RULE-001 / RULE-005）。
- **4 件は本物の違反だった。** 修正済み。

| ファイル                         | 対応                                            |
| -------------------------------- | ----------------------------------------------- |
| `apps/web/src/client/main.tsx`   | login / logout にタイムアウトを追加（RULE-001） |
| `apps/api/src/routes/ai.ts`      | `redirect: "error"` を追加（RULE-002）          |
| `apps/desktop/src/main/index.ts` | `redirect: "error"` を追加（RULE-002）          |

### 検出器そのものを検証する

「テストが緑である」ことは、検出器が正しいことを意味しない。
何も検出しない検出器も緑になる。

そこで意図的に違反を注入して、実際に落ちることを確認した。

| 注入した違反                          | 結果               |
| ------------------------------------- | ------------------ |
| `redirect: "error"` を削除            | RULE-002 が検出    |
| `signal` なしの単発 `fetch` を追加    | RULE-001 が検出    |
| 無関係な `document.body` を近くに置く | 誤って除外されない |

3 番目は、ストリーミング判定を緩く書くと
`document.body` のような無関係な `.body` でルールが黙って適用されなくなるためである。
**判定は必ず厳しい側（違反とみなす側）へ倒す。**
見逃しは緑になって気付けないが、誤検出は目に見えて直せる。

## 既知の限界

黙って誤動作させないために、限界を明示しておく。

- **RULE-002 の検出はインライン記述のみ。**
  `fetch()` の引数に直接書かれたヘッダしか見ない。
  `Headers` オブジェクトを別の場所で組み立ててから渡す書き方
  （`apps/web/src/worker/index.ts` のプロキシがこれ）は検出できない。
  テストが緑でも安全の証明にはならないので、資格情報を送る箇所は目視すること。
- **中継の判定は引数の形で行う。**
  すべての引数が識別子で、かつ受け皿（`globalThis.` など）を通して呼ぶものだけを中継と見なす。
  受信側の名前で除外していた頃は `globalThis.fetch("...", { headers })` のような
  実際の呼び出しまで隠れていた（PR#98 のレビューで発覚）。判定は違反側へ倒す。
- **収穫ツールは実行者を PR 作成者と見なす。**
  複数人で開発するようになったら、PR ごとの作成者を引く必要がある。
- **返信せず直接修正した指摘は「未対応」に見える。** 対応件数は下振れする。
- **クラスタはレビュー当時のパスで束ねる。**
  大きなディレクトリ移動があると、同じ問題が移動の前後で別クラスタに割れる
  （例: PR#48 のモノレポ移行で `src/` から `apps/vscode-extension/src/` へ移った分）。

## 今後

- **セッション中の指摘は拾えていない。**
  この仕組みが原料にするのは PR レビューだけで、
  作業中に人がエージェントへ与えた訂正（「そうじゃない」）は入り口がない。
  導入済みの `hookify` プラグインがこの領域を扱うので、別途検討する。
- **CodeRabbit へルールを流し込む。**
  `.coderabbit.yaml` の path-based instructions に同じルール群を渡せば、
  CodeRabbit が同じ指摘を繰り返す代わりに、
  このプロジェクト固有のルールを検査するレビュアーになる。ループが閉じる。
- **設計文書のレビューは別問題として扱う。**
  実測では `docs/auth.md` が 13 件と最多のレビューを集めており、
  どのコードファイルよりも多い。これはコード規約ではなく設計文書レビューのパターンなので、
  コードのガードレールとは別に考える必要がある。
  収穫ツールは現状これを候補から除外している。
