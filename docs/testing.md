# テスト方法

現時点では自動テストを持たない。手動での動作確認手順をここにまとめる。

自動テストの方針は末尾の「自動テストについて」を参照。

## 前提

- Node.js 22.13.0 以上（ESLint 10 の要求）
- 初回のみ `npm install`

## 1. コマンドラインでの確認

コードを書き換えたら、まずこの3つを通す。PRを出す前にも実行する。

```bash
npm run compile        # 型が通るか。out/ に成果物が出る
npm run lint           # 書き方の規約に反していないか
npm run format:check   # 整形済みか。崩れていれば npm run format で直す
```

いずれもエラーが無ければ何も表示されずに終了する。

### ESLintルールの確認

`src/ai/` から `vscode` を import できないルールが効いていることを確認する場合は、一時的に次のファイルを作って `npm run lint` を実行する。

```ts
// src/ai/_probe.ts
import * as vscode from "vscode";
export const probe = vscode.version;
```

`no-restricted-imports` のエラーが出れば正常。確認後はファイルを削除する。

## 2. 拡張の動作確認

1. VS Code でこのリポジトリを開く
2. 右下に推奨拡張機能のインストールを促されたら入れる（ESLint / Prettier）
3. `F5` を押す
4. 別ウィンドウが開く。タイトルバーに `[拡張機能開発ホスト]` と表示されていれば起動成功
5. 開発ホスト側のウィンドウで適当なファイルを開く
6. コードを選択して `Ctrl + Shift + J`（mac は `Cmd + Shift + J`）
7. **元のウィンドウに戻り、「デバッグ コンソール」パネルを確認する**

### ログの出る場所

出力先は**「デバッグ コンソール」であり、ターミナルではない**。ここが最もつまずきやすい。

開発ホストでは他の拡張も同時に動くため、無関係なログが多く混ざる。自分のコードの出力かどうかは、`console.log` した内容と一致するかで判断する。

## 3. 確認項目

| #   | 操作                                          | 期待する結果                                           | 関連Issue |
| --- | --------------------------------------------- | ------------------------------------------------------ | --------- |
| 1   | コードを選択して `Ctrl + Shift + J`           | デバッグコンソールに選択した文字列が出る               | #8        |
| 2   | 複数行を選択して実行                          | 改行が保持されたまま出力される                         | #8        |
| 3   | 何も選択せずに実行                            | 「コードを選択してください」の通知が出る               | #8        |
| 4   | エディタを1つも開かずに実行                   | 何も起きない。エラーにならない                         | #8        |
| 5   | コマンドパレットで `Code Companion` を検索    | 「Code Companion: Ask Selection」が候補に出る          | #6        |
| 6   | ターミナルにフォーカスして `Ctrl + Shift + J` | 発火しない（`when: editorTextFocus` のため仕様どおり） | #7        |
| 7   | 拡張を再読み込みして 1 を再実行               | コマンドが重複登録されず、正常に動く                   | #6        |

6 と 7 は正常系に見えないが、いずれも意図した挙動なので確認対象に含める。

### OS別の確認

キーバインドの衝突確認は実機が必要なため、担当者が分かれる。

- [ ] Windows
- [ ] macOS
- [ ] Linux

## 4. うまくいかないとき

| 症状                             | 原因と対処                                                                           |
| -------------------------------- | ------------------------------------------------------------------------------------ |
| 何も出力されない                 | ターミナルを見ている可能性がある。「デバッグ コンソール」パネルに切り替える          |
| ショートカットが反応しない       | エディタ本体にフォーカスが必要。ターミナルやサイドバーにフォーカスがあると発火しない |
| コードを直したのに反映されない   | `tsc -watch` は自動で再ビルドするが、開発ホスト側は `Ctrl + R` でリロードが必要      |
| `F5` でビルドが走らない          | `.vscode/tasks.json` の watch タスクが動いているか確認する                           |
| `npm install` で EBADENGINE 警告 | Node が 22.13.0 未満。22.13 以上か 24 LTS に上げる                                   |

`console.log` の行にブレークポイントを置けば、変数の中身を止めて確認できる。

## 自動テストについて

現時点では導入しない。VS Code拡張のテストはテストのたびにVS Code本体を起動する仕組みが必要で、セットアップも実行も重い。現在の実装量に対して割に合わない。

導入を判断するのは AI/01 (#10) に着手するタイミングとする。`src/ai/` は ESLint のルールにより `vscode` へ依存しない純粋な TypeScript になるため、VS Code を起動せずに通常の単体テストが書ける。プロンプトの組み立て（AI/03 #12）は、まさにテストで守りたい対象である。
